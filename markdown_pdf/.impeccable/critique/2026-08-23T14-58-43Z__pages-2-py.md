## Design Specificity Verdict

基线页面功能扎实，但视觉与信息架构更像通用 Streamlit 表单。最需要产品化的地方不是增加装饰，而是把“原文来源 → 摘要目的 → 结果与再生成”变成一个可预测闭环。

独立设计评审指出模式命名、PDF 重新读取和输入渠道是主要认知负担。确定性检测返回 `[]`，说明没有命中机械反模式；浏览器证据确认桌面与 390px 手机宽度均无横向溢出、按钮在移动端达到 44px。两者并不冲突：问题主要是信息架构与文案，而不是 CSS 违规。

## Overall Impression

底层能力比界面表达成熟。最大机会是让用户不必先理解“摘要算法”，只需按自己的阅读目的选择。

## What's Working

- API Key 缺失时明确说明并禁用生成，系统状态清楚。
- PDF 提取、摘要导出和移动端堆叠已有可靠基础。
- 页面保持克制的中性色和标准 Streamlit 控件，没有装饰性噪音。

## Priority Issues

- **[P1] 三种模式边界不可见**：用户只能看到名称，必须试错。修复为在决策点直接显示输出结构、长度与适用场景，默认核心摘要。Suggested command: `$impeccable clarify`。
- **[P1] PDF 读取与重新生成闭环不清**：生成后原文入口被折叠，同一文件无法主动恢复。修复为原文来源始终可见，显示页数/字符数，并增加“重新读取这个文件”。Suggested command: `$impeccable distill`。
- **[P1] 缺少网页文章入口**：微信公众号内容需要手工复制。修复为同一来源控件内加入文章网址，并提供抓取限制与粘贴替代路径。Suggested command: `$impeccable shape`。
- **[P2] 次要功能竞争注意力**：提示词、隐私、PDF/长图导出分散主流程。修复为渐进披露，结果区只保留复制、Markdown 下载和发送到 PDF。Suggested command: `$impeccable distill`。

## Persona Red Flags

- **Jordan（首次使用）**：无法从“快速/核心/分章节”推断会得到什么；PDF 解析完成后的下一步不够明显。
- **Sam（依赖无障碍）**：基线使用原生控件和标签是优点，但模式差异主要靠记忆，状态关系缺少就地说明。
- **Casey（移动端）**：页面无横向溢出且按钮尺寸合格，但生成后再找输入入口需要较多滚动和上下文切换。

## Minor Observations

- 微信公众号可能因登录、验证码或频率限制无法由服务器直接读取，需要明确备用路径。
- URL 获取必须阻止内网、本机和不安全重定向，避免把便利功能变成 SSRF 入口。

## Questions to Consider

- 用户是在选择“摘要算法”，还是在表达“先快速判断 / 日常理解 / 沿结构研究”？
- 同一个 PDF 被编辑后，恢复原文件是否应该是一个显式、可逆动作？
- 当公众号无法抓取时，能否让用户立即知道下一步是复制正文，而不是只看到网络错误？
